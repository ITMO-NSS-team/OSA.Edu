# OSA.Edu

OSA.Edu — система автоматической проверки выпускных квалификационных работ и диссертаций.

Система анализирует структуру документа, находит ключевые разделы работы и проверяет текст по набору формальных и смысловых правил. Для простых проверок используется Python-код, для смысловых проверок — LLM через OpenRouter.

Отдельный режим «Проверка воспроизводимости» сопоставляет технические утверждения из PDF-файла ВКР с программным кодом указанного репозитория: находит подтверждения в коде, показывает результат проверки каждого утверждения, уровень уверенности и объяснение. Результаты можно сохранить в JSON или сформировать PDF-отчёт на русском или английском языке.
Отдельный режим «Нормоконтроль» отправляет PDF на внешний MCP-сервер «Автонормоконтроль», отслеживает попытки выполнения и скачивает готовый PDF-отчёт.

Отдельный режим «Проверка литературы» проверяет библиографические ссылки из PDF: извлекает список источников, классифицирует тип источника, ищет DOI, arXiv, URL и Crossref-подтверждения, сверяет метаданные и выносит сомнительные записи в отдельный список для ручного просмотра.

Эксперименты для AAAI 2026 demo находятся в `experiments/aaai_demo_2026`: там собраны скрипты, промпты, конфиги и агрегированные таблицы результатов для трёх оценочных экспериментов.

## Что умеет OSA.Edu

OSA.Edu позволяет:

- загружать работы в формате PDF и DOCX;
- автоматически извлекать текст и структуру документа;
- находить введение, цель, задачи, положения на защиту, главы, выводы, заключение и список литературы;
- проверять работу по формальным и смысловым правилам;
- проверять сокращения, оформление, библиографию, структуру положений и другие элементы;
- отправлять PDF на внешний MCP-сервер нормоконтроля и скачивать итоговый PDF-отчёт;
- отдельно проверять литературу и ссылки на источники: существование источника, совпадение названия, авторов, года, DOI/arXiv/URL и других метаданных;
- вести очередь проверки литературы для нескольких PDF и выгружать результат в TSV;
- показывать доказательства найденных нарушений с привязкой к тексту документа;
- отмечать неоднозначные проверки для ручного просмотра;
- формировать пользовательский и технический отчёты.

# Быстрый запуск

## Требования

Перед запуском установите:

- Python 3.11–3.14
- Node.js 20.19+
- npm
- Git

Также необходим API-ключ OpenRouter.

---

## 1. Клонирование репозитория

```bash
git clone https://github.com/ITMO-NSS-team/OSA.Edu.git
cd OSA.Edu
```

---

## 2. Создание Python-окружения

### Windows PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### Linux / macOS

```bash
python3 -m venv .venv
source .venv/bin/activate
```

---

## 3. Установка Python-зависимостей

```bash
pip install -r requirements.txt
```

Основные зависимости backend:

- FastAPI
- Uvicorn
- PyMuPDF
- httpx
- fastmcp
- python-docx
- ReportLab
- OSA (`osa_tool`)
---

## 4. Установка frontend-зависимостей

```bash
npm install
```

---

## 5. Настройка OpenRouter

Создайте `.env` из примера:

### Windows

```powershell
Copy-Item .env.example .env
```

### Linux / macOS

```bash
cp .env.example .env
```

Добавьте API-ключ:

```env
OPENROUTER_API_KEY=your_api_key
```

---

## 6. Запуск

```bash
npm run dev
```

Команда запускает одновременно:

- FastAPI backend — `http://127.0.0.1:8787`
- React frontend — `http://127.0.0.1:5173`

Откройте в браузере:

```text
http://127.0.0.1:5173
```

---

## 7. Запуск в Docker Compose dev mode

Docker-режим запускает frontend и backend в отдельных контейнерах:

- FastAPI backend — `http://127.0.0.1:8787`
- React frontend — `http://127.0.0.1:5173`

Dev Compose использует host network mode, чтобы backend видел VPN-маршруты хоста и host-local ссылки внешнего нормоконтроля. Сначала создайте `.env` и добавьте `OPENROUTER_API_KEY`, как описано выше. Затем запустите:

```bash
docker compose -f docker-compose.dev.yml up --build
```

Runtime-данные backend сохраняются в именованном Docker volume `osa-edu-dev_backend_data`, поэтому загрузки и `jobs.json` переживают перезапуск контейнеров.

Для вкладки «Нормоконтроль» backend должен иметь сетевой доступ к MCP endpoint из `.env`; при Docker-запуске это обеспечивается host network mode.

MCP-вызовы во вкладке «Нормоконтроль» ограничены отдельным deadline на попытку. По умолчанию backend делает 3 попытки по 30 секунд для `list_tools`, `submit_document` и `generate_pdf_report`; скачивание готового PDF-отчёта использует отдельный HTTP timeout 120 секунд.

# Как пользоваться

## Проверка работы по правилам

После запуска приложения:

1. Откройте страницу проверки.
2. Выберите PDF или DOCX файл.
3. Выберите модель.
4. Запустите обработку.
5. Дождитесь построения структуры документа.
6. При необходимости проверьте найденные разделы.
7. Подтвердите структуру.
8. Дождитесь окончания проверки правил.
9. Просмотрите найденные нарушения.
10. Скачайте необходимый отчёт.

За один запуск backend поддерживает загрузку нескольких файлов.

## Нормоконтроль

Для отдельного нормоконтроля через MCP:

1. Откройте вкладку «Нормоконтроль».
2. При необходимости нажмите «Проверить MCP», чтобы убедиться, что endpoint доступен.
3. Загрузите один PDF-файл.
4. Запустите нормоконтроль и дождитесь завершения внешнего DAG.
5. Если проверка завершилась ошибкой, откройте журнал MCP с попытками и сообщениями внешнего сервера.
6. Скачайте готовый PDF-отчёт нормоконтроля.

## Проверка литературы и источников

Для отдельной проверки библиографического списка:

1. Откройте вкладку «Проверка литературы».
2. Выберите production-модель OpenRouter.
3. Загрузите один или несколько PDF-файлов.
4. Добавьте файлы в очередь и дождитесь завершения проверки.
5. Просмотрите источники во вкладках «Требуют внимания», «Подтверждено» и «Все».
6. Откройте найденные доказательные ссылки и скачайте TSV, если нужен табличный протокол.

Проверка литературы работает консервативно: отсутствие надёжного найденного кандидата помечается как `UNVERIFIED`, а не как доказанная фабрикация источника. Статус `LIKELY_HALLUCINATED` выставляется только при повышенной уверенности и наличии независимых веб-доказательств.

## Проверка воспроизводимости

1. Откройте вкладку «Проверка воспроизводимости».
2. Укажите URL Git-репозитория проекта.
3. Загрузите PDF ВКР.
4. Запустите проверку.
5. Дождитесь извлечения технических утверждений и их проверки по коду.
6. Просмотрите статистику, результат каждого утверждения, уверенность и найденные доказательства.
7. При необходимости скачайте JSON или PDF-отчёт.

# Как работает проверка

Общий pipeline:

```text
PDF / DOCX
    ↓
Извлечение текста и блоков
    ↓
Построение структуры документа
    ↓
Проверка и восстановление структуры
    ↓
Document Map
    ↓
Сбор фактов о документе
    ↓
Поиск кандидатов для правил
    ↓
Python / LLM проверки
    ↓
Проверка доказательств
    ↓
Результаты правил
    ↓
Отчёт
```

## 1. Извлечение документа

Для PDF используется PyMuPDF.

Документ преобразуется в набор блоков с информацией о:

- странице;
- тексте;
- координатах;
- типе блока;
- расположении внутри документа.

Это позволяет не работать с PDF как с одной большой строкой текста.

---

## 2. Document Map

После извлечения строится смысловая карта документа.

Система пытается определить:

- название работы;
- введение;
- цель;
- задачи;
- положения на защиту;
- главы;
- выводы по главам;
- заключение;
- список литературы;
- другие значимые части документа.

При этом система ориентируется не только на точное название заголовка, но и на его смысл.

Например:

```text
Цель работы
Research Goal
Objective
```

могут быть распознаны как один тип раздела — `goal`.

---

## 3. Проверка структуры

После первичного построения карта дополнительно проверяется.

Если важный раздел не был найден, система может попытаться восстановить его по:

- текстовым маркерам;
- смыслу блока;
- положению внутри документа;
- соседним разделам.

Перед глубокой проверкой структура может быть просмотрена и исправлена пользователем.

---

## 4. Проверка правил

Правила проверяются несколькими способами.

### Python detectors

Используются там, где правило можно проверить однозначно.

Например:

- оформление заголовка;
- точки и тире;
- запрещённые слова;
- нумерация;
- формат списка;
- отдельные библиографические требования.

### Candidate + LLM

Python сначала ищет потенциально подозрительные фрагменты.

LLM получает не весь документ, а только найденные кандидаты и определяет, является ли конкретный случай нарушением.

### Semantic checks

Для смысловых правил анализируется соответствующий раздел документа.

Например:

- цель работы;
- положения на защиту;
- аналоги и прототипы;
- соответствие научного результата требованиям правила.

---

## 5. Evidence

Каждое подтверждённое нарушение должно быть связано с фрагментом исходного документа.

В результате пользователь получает не только сообщение:

```text
Правило нарушено
```

но и:

```text
где найдено
↓
страница
↓
фрагмент текста
↓
объяснение
↓
рекомендация по исправлению
```

---

## 6. Нормоконтроль

Подсистема нормоконтроля запускается отдельно от основного pipeline правил и не использует Document Map.

Она выполняет следующие шаги:

```text
PDF
    ↓
Локальное сохранение файла
    ↓
MCP submit_document
    ↓
Внешний DAG нормоконтроля
    ↓
MCP generate_pdf_report
    ↓
Скачивание PDF-отчёта
    ↓
Журнал попыток, ошибки, предупреждения и готовый отчёт
```

Backend хранит локальную очередь задач, фиксирует параметры MCP endpoint и DAG, показывает попытки `list_tools`, `submit_document` и `generate_pdf_report`, а при успешном завершении сохраняет скачанный PDF-отчёт.

---

## 7. Проверка литературы и источников

Подсистема проверки литературы запускается отдельно от основного pipeline правил.

Она выполняет следующие шаги:

```text
PDF
    ↓
Поиск и извлечение списка литературы
    ↓
Нормализация отдельных библиографических записей
    ↓
Классификация типа источника
    ↓
DOI / arXiv / direct URL / Crossref precheck
    ↓
Детерминированное сравнение метаданных
    ↓
LLM-сравнение неоднозначных кандидатов
    ↓
Углублённая веб-проверка сомнительных источников
    ↓
Статусы, доказательные ссылки и TSV
```

Для каждой записи система пытается определить тип источника: статья, препринт, книга, стандарт, отчёт, dataset, документация, репозиторий, веб-источник или другой источник. Сильные совпадения по идентификаторам и метаданным решаются детерминированно, а LLM используется для неоднозначных случаев и веб-проверки.

Результат содержит исходную запись, найденную библиографическую запись, evidence URL, статус и комментарий. Основные статусы:

- `OK` — источник подтверждён;
- `OK_MINOR_MISMATCH` — источник найден, но есть небольшие расхождения;
- `METADATA_MISMATCH` — найденный источник конфликтует с записью в работе;
- `SUSPICIOUS` — запись требует ручной проверки;
- `LIKELY_HALLUCINATED` — источник с высокой вероятностью не подтверждается;
- `UNVERIFIED` — надёжного подтверждения не найдено;
- `ERROR` — техническая ошибка проверки.

# Отчёты

После завершения проверки доступны несколько форматов.

### Пользовательский PDF

Краткий отчёт для автора работы.

Содержит:

- основные нарушения;
- понятное объяснение;
- доказательства;
- рекомендации по исправлению.

### Developer PDF

Расширенный технический отчёт.

Дополнительно содержит:

- способ проверки правила;
- coverage;
- технические статусы;
- evidence;
- диагностику LLM;
- информацию о структуре документа.

### JSON

Полный структурированный результат проверки.

Удобен для:

- интеграций;
- автоматической обработки;
- тестирования;
- сравнения результатов разных версий checker-а.

### Markdown

Текстовая версия технического протокола.

### TSV проверки литературы

На странице «Проверка литературы» результат можно скачать как TSV: номер источника, тип источника, verdict/status, исходная запись, найденная запись, evidence URL и комментарий.

### PDF-отчёт нормоконтроля

На странице «Нормоконтроль» после успешного внешнего запуска доступен скачиваемый PDF-отчёт, сгенерированный MCP-сервером «Автонормоконтроль».

В `.env.example` также находятся параметры:

- восстановления кандидатов;
- обработки сокращений;
- MCP endpoint, DAG, количества попыток и timeouts для вкладки «Нормоконтроль»: `NORMCONTROL_MCP_URL`, `NORMCONTROL_DAG_ID`, `NORMCONTROL_MCP_ATTEMPTS`, `NORMCONTROL_MCP_ATTEMPT_TIMEOUT_SECONDS`, `NORMCONTROL_HTTP_TIMEOUT_SECONDS`;
- модели и веб-этапа проверки литературы: `LITERATURE_REVIEW_MODEL`, `LITERATURE_WEB_SEARCH_ENABLED`, `LITERATURE_WEB_FALLBACK_TO_PLUGIN`, `LITERATURE_WEB_SEARCH_ENGINE`, `LITERATURE_WEB_PROVIDER_ORDER`;
- опционального контакта для polite pool Crossref: `CROSSREF_MAILTO`.
- параметры проверки воспроизводимости: модель OSA, timeout, context window, max tokens и количество повторов (`REPRODUCIBILITY_*`);
Обычно значения по умолчанию менять не требуется.

# Что делать при ошибке проверки

Если отдельные LLM-проверки не завершились, можно повторить только их:

```text
Retry failed
```

Если нужно заново выполнить всю проверку правил по уже готовой структуре:

```text
Retry
```

Если необходимо заново построить Document Map:

```text
Restart
```

# Ограничения

OSA.Edu является автоматическим помощником нормоконтроля.

Результат проверки:

- может содержать ложные срабатывания;
- может не обнаружить отдельные нарушения;
- смысловые проверки могут требовать ручного подтверждения;
- результат не является официальным решением о допуске работы к защите.

Особое внимание рекомендуется уделять правилам, отмеченным системой как неоднозначные или технически не завершённые.

# Проверка воспроизводимости

Отдельная вкладка «Проверка воспроизводимости» позволяет проверить, насколько утверждения из текста ВКР подтверждаются программным кодом проекта.

Для запуска проверки пользователь указывает:

- ссылку на репозиторий проекта;
- PDF-файл ВКР.

После этого OSA.Edu анализирует текст работы, выделяет проверяемые технические утверждения (claims) и сопоставляет их с содержимым репозитория.

Например, если в работе утверждается, что реализован определённый алгоритм, используется конкретная модель или предусмотрен механизм резервного переключения, система пытается найти подтверждение этому в коде проекта.

Для каждого утверждения пользователь получает:

текст утверждения из ВКР;
результат проверки;
уровень уверенности;
раздел работы, из которого оно было извлечено;
файл или другой фрагмент репозитория, подтверждающий результат;
краткое объяснение.

На странице также отображается общая статистика: сколько утверждений было выделено, сколько проверено, сколько подтверждено и сколько исключено из проверки.

Результат анализа можно сохранить в JSON, а также сформировать отчёт в PDF на русском или английском языке.
